# 原型与页面规格的差异清单

对照对象：

- 规格：`docs/00-product/page-spec.md`（P01–P13 + 三个追加页面，提交 `6393a77`）
- 原型：`prototype-web/`（提交 `c63f9b7`）

原则：**本轮不改原型**，只把对不上的地方列出来，供组内评审后统一处置。每条差异都有编号，后面评审记录、issue、提交信息可以直接引用 `D-xx`。

差异分四级：

| 级别 | 含义 | 处置预期 |
| --- | --- | --- |
| P0 | 影响验收或会被老师追问的硬缺口 | 合并前必须解决或书面说明 |
| P1 | 与规格不一致但可在开发期修正 | 排进下一轮 UI 迭代 |
| P2 | 命名、文案、呈现方式差异 | 顺手统一即可 |
| Q | 需产品/后端确认后再定 | 不擅自改，等结论 |

## 一、页面级差异

| 编号 | 级别 | 规格 | 原型 | 差异说明 |
| --- | --- | --- | --- | --- |
| D-01 | P1 | P01 注册与登录（同一页） | `login.html` + `register.html`（两页） | 视觉上拆成两页。规格把注册与登录视为一个页面单元，验收用例也按 UC-01/UC-02 分开写，所以拆分本身不矛盾，但**页面编号对不上**，PR 描述或评审时需说明 1:2 的映射 |
| D-02 | P0 | P03 模拟行程上报（独立页） | 合并进 `app/index.html` 首页 | 首页内嵌上报表单，未独立成页。好处是少一次跳转；风险是规格要求的"失败保留输入、超时重试、clientTripId 提示"在首页里空间不足，届时要么改回独立页，要么在首页做展开态 |
| D-03 | P0 | P04 行程与核算明细（独立页，含输入、基准/实际因子、减排、积分、规则版本、计算时间） | `app/trips.html` 只有列表，无详情页 | 列表行里只有方式、里程、减排、积分、单号、规则版本；**缺少基准因子、方式因子、实际因子、计算时间、9 位原精度**这些"可解释性"字段。P04 的验收关注就是"快照可解释"，目前不满足 |
| D-04 | P1 | P05 积分账户 + P06 积分流水（两页） | `app/points.html` 一页（hero + 流水表） | 合并展示。信息没丢，但规格要求流水"分页"、账户页有独立"查看流水"入口，合并后这两个行为没有落点 |
| D-12 | P0 | P13 积分对账（管理员只读核对） | **无对应页面** | 完全缺失。规格明确"读取失败显示核对失败，不能显示为无差异""差异是报告，不触发修复"，属于验收会看的点 |
| D-13 | P1 | 追加页面：个人资料（US-03） | **无独立页**（`me.html` 只存在于已废弃的移动端原型 `prototype/`） | Web 端没有"我的/个人资料"入口，顶部头像点击无落点 |
| D-14 | P2 | 追加页面：运营统计（US-14） | `admin/dashboard.html`，标题写作「运营概览」 | 同一页两种叫法，建议统一为规格用词「运营统计」，或反向让规格改称「运营概览」 |
| D-19 | P2 | P02 首页导航含「我的」入口 | 顶部导航只有 首页/行程/积分/商城/订单 | 与 D-13 同源，导航少了个人中心 |

其余页面一一对应、无差异：P02→`app/index.html`、P07→`app/mall.html`、P09→`app/orders.html`、P10→`admin/rules.html`、P11→`admin/products.html`、P12→`admin/orders.html`、追加页「用户启停（US-15）」→`admin/users.html`。

## 二、字段级差异

| 编号 | 级别 | 规格要求 | 原型现状 | 影响 |
| --- | --- | --- | --- | --- |
| D-15 | P0 | 减排量原精度 9 位，页面展示 6 位并标注「展示值已舍入」；积分由后端原精度核算 | 页面展示 2 位小数（如 `1.50 kg`），无舍入说明 | 会被问"你说的四舍五入到 0.01 是前端还是后端算的"——这是碳核算最容易翻车的点 |
| D-16 | P0 | P03 需 出行方式 + 里程 + 起终点 + 开始/结束时间；`startTime < endTime ≤ 服务器当前时间` | 表单只有 出行方式 + 里程 + 用时（分钟），无起终点、无起止时间 | 规则里 `BR-01` 依赖"按行程结束时间选规则版本"，没有结束时间就无法判定版本；"用时"是原型自造的字段，规格里不存在 |
| D-17 | P1 | 里程 > 0 且 ≤ 200 km，最多 3 位小数 | 无上限、无小数位校验，仅做实时估算 | 前端缺预校验，服务端会拒，体验上是提交后才报错 |
| D-18 | P1 | P06 流水、P09 订单需分页 | 均为静态列表，无分页控件 | 数据量一多就不可用，且规格把它写进验收关注 |
| D-05 | P1 | P07/P11 商品需体现**商户归属**（merchantId） | 商城卡片和库存表都没有商户字段 | 商户是领域模型里的实体（`Merchant`），管理端"代商户操作"的表述没有依据 |
| D-06 | P0 | P08 兑换数量为**正整数**，显示预计总积分 | `product.html` 数量固定为「1 份」，无步进器 | 多件兑换无法演示，直接卡住 P08 的验收 |
| D-08 | P1 | P09 订单需展示**原单价与成本快照**、数量、取消原因 | 订单卡片只有金额和状态，无单价快照、无取消原因字段 | 与 `BR` 里的"价格快照不随现价变化"对不上 |
| D-09 | P2 | P10 有效期左闭右开，空结束代表无穷远；表单不允许改写已发布因子 | 规则页有「变更原因（必填）」「同一天同一方式只允许一条生效规则」，但**未写左闭右开**，也未说明旧版本只读 | 规则版本语义靠口头解释，容易误改 |
| D-10 | P1 | P11 商品变更需记录**变更原因** | 商品页只有上下架与库存，无变更原因字段 | 与规则页的处理不一致（规则有原因、商品没有） |

## 三、交互与状态差异

| 编号 | 级别 | 规格要求 | 原型现状 |
| --- | --- | --- | --- |
| D-07 | P1 | P08 请求前生成 `requestId`，同键同商品同数量重放原订单；二次确认只是防误操作 | 有「为什么不能重复点击」说明与按钮禁用，但没体现 requestId 的生成与重放语义 |
| D-11 | P0 | P12 取消原因**必填**；确认文案写明返还原订单积分与数量 | 取消弹窗是二次确认，**无原因输入框**，文案写了退还但没写数量 |
| D-20 | P1 | 所有加载数据的页面提供 加载/空/成功/失败 四态，无权限单独提示 | 静态原型只有成功态与少量空态（缺货、积分不足），没有加载骨架与失败态示例 |
| D-21 | P2 | 401/403/404/409/500 分别提示；超时文案「结果尚未确认，请保留本次请求后重试或查询记录」 | 统一 toast，文案未区分状态码 |
| D-22 | Q | 首页"本周概览""累计获得/兑换"等聚合数字 | 规格 P02 强调"仅本人数据，不混用汇总与单次结果"，原型的聚合块需确认数据口径（本周 vs 本月 vs 累计） |

## 五、未冲突但建议确认

1. **商城排序**：原型默认「按积分从低到高」，规格未规定排序规则。要么写进规格，要么改成默认综合排序。
2. **首页快捷入口**：原型有「上报行程/行程记录/积分商城/积分明细」四个快捷块，规格未提，属可选增强。
3. **规则试算器**：`admin/rules.html` 的试算器是原型自加的校验工具，规格没有。建议保留并写进规格——它正好演示 `BR-02` 公式。
4. **管理端侧栏 5 项**：规格 P10–P13 只列 4 个管理页，原型多了「用户管理」（对应追加页 US-15）。若 US-15 本轮不做，`users.html` 应隐藏。
5. **演示账号**：`shengyang / admin` 是假数据，接口联调时要换成后端种子账号，避免答辩时对不上。
