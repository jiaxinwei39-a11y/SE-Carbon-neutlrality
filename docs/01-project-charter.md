## 1. 项目背景

城市绿色出行推广需要将低碳行为转化为市民可感知、可积累和可兑换的激励。本项目通过模拟公交、地铁、骑行等出行记录，计算相对基准出行方式的碳减排量，并将减排结果转换为积分。用户可以查询积分并在商城兑换商品，运营人员负责规则、商品、库存和异常处理，商户参与商品供给和兑换履约。

本项目同时承担软件工程课程实验目标，要求在开发过程中完成需求分析、UML 建模、敏捷迭代、团队协作、测试验证和规范文档编写，并对 AI 辅助生成的内容进行人工审查和验证。

## 2. 项目目标

1. 建立一条可验收的核心业务闭环：上报出行、计算碳减排量、发放积分、查询积分、浏览商品、兑换商品。
2. 通过领域事件解耦行程核算、积分发放、库存预占、积分扣减和兑换履约等环节。
3. 保证积分和库存数据在重复请求、消息重投和并发兑换场景下仍然准确一致。
4. 使用可运行的软件增量体现敏捷开发过程，每个 Sprint 结束时完成演示、测试和回顾。
5. 形成需求模型、分析模型、设计模型、测试证据和实验报告之间的可追踪关系。
6. 在 AI 辅助开发中保留人工决策、修改和验证记录，体现“AI 辅助，人决策”。

## 3. 项目范围

MVP 范围以“用户出行后获得积分并完成一次兑换”为主线，详细功能边界见 [MVP 范围与验收基线](02-mvp-scope.md)。

MVP 包含：

- 用户注册或登录、角色权限
- 模拟出行上报和出行记录查询
- 可配置的碳减排因子和积分规则
- 碳减排量计算、积分发放和积分流水查询
- 商品浏览、详情和库存展示
- 积分兑换、库存预占、积分扣减和兑换记录
- 商品、库存、规则和订单的基础运营管理
- 领域事件、Outbox、幂等和失败补偿
- 核心单元测试、集成测试和端到端验收测试

MVP 不包含：

- 对接真实公交、地铁或骑行平台的出行数据
- 真实支付、退款和财务结算
- 手机原生 App
- 复杂反作弊、信用风控和碳交易
- 区块链积分或数字资产
- 大规模生产级高可用部署

## 4. 利益相关者

| 利益相关者 | 主要诉求 | 系统响应 |
| --- | --- | --- |
| 市民用户 | 上报方便、减排量可信、积分到账及时、兑换流程清楚 | 简化上报、展示计算明细、提供积分流水和兑换记录 |
| 运营管理员 | 规则可配置、库存可控、异常可处理、数据可审计 | 规则配置、商品与库存管理、订单查询、补偿和审计日志 |
| 商户 | 商品和库存信息准确、兑换订单明确、后续可对账 | 商户与商品关联、兑换订单视图、简化结算记录 |
| 项目小组 | 范围可控、迭代可演示、分工可追踪、文档可交付 | 清晰待办、Git 证据、UML 模型和测试报告 |
| 指导教师 | 需求、设计、实现、测试和过程材料完整且一致 | 可追踪的模型、提交记录、实验报告和互评材料 |

## 5. 成功标准

项目满足以下条件时视为达到课程实验目标：

1. 用户能够完成“登录 → 上报出行 → 查看碳减排量和积分 → 浏览商品 → 兑换商品 → 查看兑换记录”的完整流程。
2. 在相同输入和相同规则版本下，碳减排量与积分计算结果可重复，并能追溯使用的因子和规则。
3. 重复提交、消息重投或并发兑换不会造成重复加分、重复扣分、超卖或孤立订单。
4. 核心积分模块具备单元测试，关键集成流程使用真实 MySQL 和 RabbitMQ 进行集成测试。
5. 每个 Sprint 都有可运行增量、评审记录和 Git 提交证据。
6. UML 分析模型、设计模型、代码、测试用例和实验报告能够相互追踪。
7. 团队完成 Git 协作、组内互评、AI 使用记录和打印版及电子版实验报告。

## 6. 团队角色与治理

实际成员姓名由组长在团队确认后补入。建议职责如下：

| 角色 | 主要职责 | 核心交付物 |
| --- | --- | --- |
| 组长/需求与账户 | 范围管理、待办列表、需求模型、账户模块、会议和报告统筹 | 项目章程、用户故事地图、用例模型、账户模块、互评汇总 |
| 行程与积分核心 | 出行记录、碳核算、积分规则、积分流水和余额一致性 | 行程与积分模块、核心测试、相关时序图和状态图 |
| 商城与基础设施 | 商品、库存、兑换、事件机制、Docker、CI 和运营接口 | 兑换模块、事件契约、组件图、部署图 |
| 前端与联调 | 用户端、运营端、接口联调、状态和异常展示 | 页面原型、前端功能、联调记录 |
| 测试与交付 | 测试计划、集成测试、端到端测试、AI 记录和报告校对 | 测试报告、验收证据、报告附件和最终检查 |

治理原则：

- 每个业务模块只有一个主负责人，但至少有一名其他成员参与评审。
- 模块负责人同时负责对应的需求澄清、UML 子模型、测试用例和报告章节。
- 范围变更必须形成 Issue，说明原因、影响和验收标准，由组长和相关模块负责人确认。
- 所有功能通过 Pull Request 合并，不在 `main` 分支直接提交功能代码。

## 7. 敏捷协作约定

- 采用 1–2 周一个 Sprint，Sprint 0 为需求与工程准备阶段，可控制在 3–5 天。
- 每个 Sprint 开始前确认 Sprint 目标和验收标准，结束时进行演示、评审和回顾。
- 每个 Sprint 必须产生可运行、可演示的软件增量，并创建 Git 标签。
- Issue 至少包含背景、验收标准、负责人、优先级和关联模型。
- 分支建议使用 `feature/*`、`fix/*`、`docs/*`；提交建议使用 `feat:`、`fix:`、`test:`、`docs:` 等前缀。
- 每个 Pull Request 至少由一名非作者成员评审，并附测试结果。
- 团队固定每周例会和每日短同步，会议结论写入仓库文档或看板。

## 9. 主要风险

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 范围过大 | 核心流程未完成，测试和报告仓促 | 严格执行 MVP 边界，非核心功能放入后续版本 |
| 积分计算规则含糊 | 结果不可复现，测试无法验收 | 先确定公式、取整、上限、规则版本和样例 |
| 积分与库存并发不一致 | 重复扣分、超卖或订单异常 | 幂等键、不可变流水、事务、唯一约束和集成测试 |
| 事件驱动引入最终一致性 | 页面状态不明确，失败后难以恢复 | Outbox、消费者幂等、重试、死信队列和补偿事件 |
| 模型与代码脱节 | 报告和答辩材料不一致 | 每个模块维护对应 UML 子模型并纳入评审 |
| Git 集中在最后提交 | 无法证明协作过程 | 每个 Issue 对应分支和 PR，每周检查提交记录 |
| AI 生成内容未验证 | 代码、规则或文档出现隐蔽错误 | AI 使用记录、人工评审、测试验证和决策说明 |
