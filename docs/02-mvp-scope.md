# MVP 范围与验收基线

## 1. MVP 定义

MVP 要让一名用户独立完成以下闭环：

> 登录系统，上报一条模拟绿色出行记录，查看系统计算的碳减排量和积分，浏览商城商品，使用积分兑换商品，并查询兑换结果；运营人员能够维护商品和库存，并处理异常订单。

该闭环必须建立在积分流水、库存和领域事件可靠一致的基础上，不能只完成页面演示。

## 2. 范围优先级

### P0：MVP 必须完成

| 模块 | 必须实现的能力 | 验收重点 |
| --- | --- | --- |
| 账户与权限 | 注册或登录、用户角色、管理员角色、商户数据归属 | 未登录不能访问受保护接口，普通用户不能调用运营接口 |
| 行程上报 | 模拟公交、地铁、骑行等出行记录，录入距离、时间和客户端行程号 | 重复上报同一条行程不会重复发分 |
| 碳核算 | 根据基准排放和实际排放计算减排量，保存规则和因子快照 | 同一规则版本下可复现，异常输入被拒绝 |
| 积分账户 | 积分发放、查询余额、查询流水、每日上限 | 余额与流水汇总一致，发放积分可审计 |
| 商品浏览 | 商品列表、详情、价格和库存展示 | 下架商品不可兑换，库存状态准确 |
| 积分兑换 | 校验积分与库存、预占库存、扣减积分、生成订单 | 余额或库存不足时不产生部分扣减 |
| 兑换记录 | 用户查看订单及处理状态 | 状态变化清晰，不出现无主订单 |
| 运营管理 | 商品维护、库存调整、规则配置或种子配置、订单查询 | 操作有权限限制和审计记录 |
| 事件处理 | 行程、核算、积分的领域事件，Outbox 和消费者幂等 | 消息重复投递不造成重复业务结果 |
| 测试 | 核心单元测试、关键集成测试和端到端验收 | 正常流程和失败补偿均可验证 |

### P1：MVP 后优先增强

- 商户查看自己商品和兑换订单
- 简化商户结算汇总
- 运营数据概览和导出
- 用户消息通知
- 行程异常申诉
- 活动倍率和积分排行榜

### P2：可选扩展

- 积分即将过期提醒
- 商品推荐
- 碳减排月度报告
- 管理端操作审计查询页面
- 多城市和多运营区域配置

### 明确不做

- 真实公交卡或出行平台接口
- 真实支付、发票和财务退款
- 原生 Android/iOS App
- 基于位置轨迹的反作弊
- 区块链积分
- 碳配额交易
- 生产级多集群高可用部署

## 3. 核心业务规则

以下规则是 MVP 的统一定义。具体因子和积分系数由数据库中的规则配置提供，本文不虚构未经确认的行业数值。

### 3.1 碳减排量

对一条出行记录：

```text
基准排放量 = 出行距离(km) × 基准排放因子(kgCO2e/km)
实际排放量 = 出行距离(km) × 实际排放因子(kgCO2e/km)
碳减排量 = max(0, 基准排放量 - 实际排放量)
```

- 基准排放因子由“被替代的常规出行方式”决定，例如小汽车基准。
- 实际排放因子由公交、地铁、骑行等方式决定。
- 因子必须带版本号和生效时间。
- 行程记录保存计算时的因子快照，历史结果不能因后来修改因子而改变。
- 距离必须大于 0，时间范围和交通方式必须合法。
- 计算结果保留的精度由统一规则确定，展示值和入账值必须使用同一结果。

### 3.2 积分生成

```text
原始积分 = 碳减排量 × 每千克积分系数 × 活动倍率
可取积分 = floor(原始积分)
本次发放积分 = min(可取积分, 当日剩余积分上限)
```

- 只在最终结果处向下取整一次，避免分步取整造成误差。
- 每日上限按用户、按自然日和业务时区计算。
- 规则版本、计算结果、取整结果和实际入账积分全部保存。
- 积分增加和扣减都通过不可变流水记录，不能只修改余额数值。
- 积分流水需要唯一业务键，防止同一行程或同一兑换请求重复入账。

### 3.3 积分账户一致性

- 积分余额必须等于所有有效积分流水的汇总结果。
- 余额表可以作为查询优化，但必须与流水在同一事务内更新，并定期进行一致性校验。
- 任何积分调整都必须生成流水并记录操作者、原因和来源。
- 不允许普通业务接口直接覆盖余额。

### 3.4 积分兑换

兑换按以下业务顺序执行：

1. 校验请求幂等键，确认是否已经处理。
2. 校验商品是否上架、库存是否充足、用户积分是否充足。
3. 预占库存。
4. 扣减积分并写入兑换流水。
5. 创建兑换订单。
6. 发布兑换完成事件。

任意步骤失败时必须补偿已经完成的步骤。例如积分扣减失败后应释放库存预占，不能留下残缺订单。

### 3.5 幂等与并发

- 行程上报使用 `用户ID + 客户端行程号` 作为幂等键。
- 兑换请求使用 `用户ID + 客户端请求号` 作为幂等键。
- 相同幂等键重复提交时返回第一次处理结果，不重复加分、扣分、扣库存或创建订单。
- 库存扣减和积分扣减需要数据库事务、条件更新或乐观锁保护。
- 消息消费必须记录消费幂等键，支持至少一次投递下的安全重试。

## 4. MVP 验收场景

### 场景 A：正常出行与积分发放

**前置条件**：用户已登录，存在有效碳因子和积分规则；用户当日尚未达到积分上限。

**操作**：用户上报一条合法的模拟公交出行，携带唯一的客户端行程号。

**预期结果**：

- 生成且只生成一条出行记录。
- 保存计算使用的规则和因子版本快照。
- 计算出的碳减排量为非负数。
- 按公式生成一条正向积分流水。
- 用户积分余额增加相同数值。
- 用户能够查询到该行程和对应积分明细。

### 场景 B：重复上报不重复发分

**前置条件**：用户已经成功上报某条行程。

**操作**：使用相同客户端行程号再次提交。

**预期结果**：不新增行程、积分流水或余额变化；接口返回第一次处理的业务结果或明确的重复请求结果。

### 场景 C：积分不足时兑换失败

**前置条件**：用户积分小于商品兑换所需积分，商品有库存。

**操作**：用户发起兑换。

**预期结果**：兑换失败；用户积分、积分流水、商品库存和订单数量均不发生变化。

### 场景 D：库存不足时不超卖

**前置条件**：商品库存为 `N`，有多个用户同时兑换。

**操作**：并发发起超过 `N` 个合法兑换请求。

**预期结果**：最多 `N` 个请求成功，库存不为负数，成功订单数不超过库存数，失败请求不扣积分。

### 场景 E：中途失败能够补偿

**前置条件**：兑换流程已经完成库存预占。

**操作**：模拟积分扣减失败或订单创建失败。

**预期结果**：库存预占被释放，不出现已扣积分但无订单的情况；异常被记录并可在管理端查询。

### 场景 F：规则变更不影响历史结果

**前置条件**：用户已经完成一次出行并获得积分。

**操作**：运营人员修改碳因子或积分系数。

**预期结果**：历史出行记录和积分结果保持不变；新出行使用新生效规则。

## 5. 非功能要求

- **安全**：用户、管理员和商户按角色授权；关键接口校验资源归属。
- **可审计**：积分、库存、规则变更和兑换操作保留操作者与时间。
- **可恢复**：异步处理失败可重试，超过重试次数进入死信队列或异常记录。
- **可测试**：核心规则不依赖页面和外部服务，可使用固定规则样例进行自动化测试。
- **可部署**：使用 Docker Compose 在本机或单台云主机启动完整演示环境。
- **可追踪**：需求故事、UML 模型、接口、测试和提交记录使用统一编号关联。
- **可解释**：用户能查看碳减排量和积分的计算明细，管理员能查看规则版本。

## 6. MVP 完成判定

只有同时满足以下条件，MVP 才算完成：

1. P0 功能全部通过验收场景。
2. 核心积分和碳核算逻辑具备自动化单元测试。
3. 行程到积分、兑换成功、兑换失败补偿具备集成测试。
4. 重复提交和并发兑换测试通过。
5. 系统可通过 Docker Compose 启动并完成演示。
6. 对应用例图、类图、时序图、状态图和部署图已更新。
7. 测试报告、AI 使用记录和实验报告相关章节已形成。
