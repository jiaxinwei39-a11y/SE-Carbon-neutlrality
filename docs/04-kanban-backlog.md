# 看板初始任务

本文件用于创建 GitHub Projects、GitLab Issue Board 或其他课程看板。看板任务以可验收的小批次为单位，每个任务应指定唯一负责人和评审人。

## 1. 看板设置

建议列：

`Backlog` → `Ready` → `In Progress` → `Review/Test` → `Done`

建议标签：

- `type:requirement`、`type:design`、`type:backend`、`type:frontend`、`type:test`、`type:docs`
- `priority:P0`、`priority:P1`、`priority:P2`
- `sprint:0`、`sprint:1`、`sprint:2`、`sprint:3`
- `area:account`、`area:trip`、`area:points`、`area:mall`、`area:eda`、`area:admin`

每个 Issue 至少包含：

- 背景和目标
- 验收标准
- 负责人和评审人
- 关联用户故事、UML 图和测试编号
- 预计完成 Sprint

## 6. 就绪与完成标准

### Definition of Ready

Issue 进入 `Ready` 前应满足：

- 目标和业务价值明确。
- 验收标准可观察、可测试。
- 依赖、负责人和评审人已指定。
- 相关接口、数据或模型不再处于关键未决状态。
- 工作量适合在一个 Sprint 内完成。

### Definition of Done

Issue 进入 `Done` 前应满足：

- 验收标准全部满足。
- 代码通过 Pull Request 合并，至少一名其他成员评审。
- 单元测试或集成测试通过，关键流程附测试证据。
- 对应接口文档、UML 图和报告章节同步更新。
- 至少可以在本地演示。
- 不遗留未记录的 TODO 或已知高风险问题。
- 相关看板任务和 Sprint 目标已更新。

## 7. 分工与证据要求

- 每位成员在每个 Sprint 至少负责一个有验收标准的功能任务，并参与至少一次他人代码评审。
- 任务提交应关联 Issue 编号，例如 `feat(points): implement ledger posting (#S1-04)`。
- Sprint 结束时由模块负责人演示增量，测试负责人核对验收证据，组长记录评审结论。
- 实验报告中的分工不能只写岗位名称，应列出实际负责模块、Issue、Pull Request 和报告章节。
