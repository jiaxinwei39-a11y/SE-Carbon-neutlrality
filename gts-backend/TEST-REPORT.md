### TC-13 故障注入怎么做的

不是"逻辑上满足"，是**真的让它在中间失败**：

```properties
gts.test.fail-after-trip=true    # 行程 INSERT 之后、改账户之前抛异常
```

执行一条上报请求：HTTP 返回 `50000 服务异常`，然后核对数据库：

| 项 | 注入前 | 注入后 |
|---|---|---|
| `t_trip` 行数 | 6 | 6 |
| `t_point_ledger` 行数 | 6 | 6 |
| U001 余额 | 90 | 90 |

三样都没动，说明"插行程 → 改账户 → 写流水"确实是一个整体，中途失败全部回滚。

## 8. 第二轮评审回归（PR #30）

评审在独立环境（Java 25 编译目标 21、MySQL 8.0.46、独立测试库）复现了两个阻塞问题，
修复后按同样方式回归，**0 失败**。

### 8.1 兑换幂等：外部先锁账户 4 秒，其间发两个同键请求

复现方法：外部 MySQL 事务 `SELECT ... FOR UPDATE` 锁住 U001 账户并 `SLEEP(4)`，
窗口内并发发出两个同 `Idempotency-Key`、同商品同数量的兑换请求。

| 用例 | 前置 | 结果 |
|---|---|---|
| A1 | 库存恰好 1、价格 1 | `codes=0,0`，**同一 orderId**，订单 1 条，库存扣到 0，余额只减 1 |
| A2 | 余额恰好够一单（41 分、价格 41） | `codes=0,0`，同一 orderId，余额归 0（只扣一次） |
| A3 | 已存在订单后同键改数量 | `40904`，不再被库存/余额不足掩盖 |

### 8.2 规则禁止追溯生效

| 用例 | 输入 | 结果 |
|---|---|---|
| 过去起点 | `effectiveFrom=2026-11-01`（当天 11-17） | `40909` 拒绝 |
| 拒绝后副作用 | 检查旧规则与审计 | 旧规则 `effective_to` 仍为 NULL、审计条数不变、BUS 规则仍 1 条 |
| 当前边界 | `effectiveFrom` = 服务端当前时刻 | 接受（5 秒容差内） |
| 未来切换 | 当前 + 2 天 | 接受，旧规则被截断到当前边界 |

### 8.3 顺带修掉的缺陷

`ruleId` 只精确到秒，同一秒内连续创建两条规则会撞主键（表现为 40904）。
已改为毫秒 + 3 位随机后缀。
### 8.4 二次评审补充：追溯校验必须放在拿锁之后

评审指出：校验如果在获取规则锁**之前**执行，等待锁期间"未来"的起点会变成过去，仍会被放行
（实测等待 9 秒后 `effectiveFrom` 已过去约 7.35 秒，接口仍返回 code=0）。

修改：先锁 `t_rule_mode_lock`，再用锁内取到的服务端当前时间校验，**不设容差**。

| 用例 | 方法 | 结果 |
|---|---|---|
| 锁等待后仍拦追溯 | 外部事务锁 BUS 闸门 9 秒，其间提交"提交时刻的现在" | 请求阻塞 **8.4 秒**，返回 `40909`；服务端时间比提交时晚 9 秒 |
| 拒绝后无副作用 | 同上，检查旧规则/审计/规则数 | `effective_to` 仍 NULL、审计 0 条、BUS 规则仍 1 条 |
| 等待期间的真未来 | 锁 BUS 4 秒，其间提交"当前+5 分钟" | `code=0`，旧区间被截断到该未来时刻 |
| 明显过去（无等待） | `effectiveFrom` = 昨天 | 立即 `40909`，BUS 规则仍 2 条 |
| 其他方式不受影响 | 同一时刻提交 SUBWAY 规则 | `code=0` |
## 9. 契约冻结评审回归（PR #31）

评审在独立环境（Java 25 编译目标 21、MySQL 8.0.46）实测发现两个阻塞问题，修复后回归 **0 失败**。

### 9.1 订单快照字段没跟着放宽（Data too long）

**问题**：V3 只把 `t_product.icon` 放宽到 255，漏了兑换订单里的图标快照
`t_redemption_order.product_icon`（仍是 64）。评审用 103 字符图片 URL 的商品验证：
上架成功、兑换时报 `Data too long for column 'product_icon'`，接口返回 50000 ——
**能上架、不能兑换**。

**修复**：新增 **V4** 迁移，把 `t_redemption_order.product_icon` 同步放宽到 255；
`schema.sql` 与字典同步；创建商品时增加图标长度校验（>255 返回 40000，不再靠数据库报错）。

| 用例 | 结果 |
|---|---|
| 103 字符图标商品：创建 → 兑换 | code=0，订单快照长度 103，库里也是 103 |
| 255 字符图标商品：创建 → 兑换 | code=0，订单快照长度 255 |
| 256 字符图标：创建 | `40000`（不再 500） |
| 结构版本 | `V1,V2,V3,V4`，两个图标字段均 `varchar(255)` |

### 9.2 小数被静默截断

**问题**：`ProductPatchRequest` 用 `Long/Integer` 接收，Jackson 会把 `1.9` 截成 `1`。
评审实测 `PATCH {"points":1.9,"stock":2.9}` → **200/code=0**，实际存成 1 和 2。

**修复**：DTO 改用 `BigDecimal`，Service 里严格校验"必须是整数且在范围内"，
不合法返回 `40041` / `40042`；**所有字段先全部校验通过，再进事务落盘**。

| 用例 | 结果 |
|---|---|
| `{"points":1.9}` | `40041` |
| `{"stock":2.9}` | `40042` |
| `{"points":10,"stock":2.9}`（混合合法+非法） | `40042`，商品一个字段都没改 |
| `{"points":1.9,"status":"OFF"}` | `40041`，状态也没变 |
| `{"points":2.0}` | 接受，存为 2 |
| `{"points":1000001}` | `40041`（超出上限） |
### 9.3 schema.sql 在旧库上会"假升级"

**问题**：`schema.sql` 用 `CREATE TABLE IF NOT EXISTS`，在已存在的旧库上所有建表都会跳过
（列宽仍是旧的），但脚本末尾无条件写入 V1–V4 版本号。结果：
版本表显示已到 V4、实际列还是 `VARCHAR(64)`，而 V3/V4 迁移看到版本号已存在就拒绝执行——
**旧库再也升不上来，而且版本表在撒谎**。

**修复**：`schema.sql` 开头加安装闸门——检测到 `t_schema_version` 表已存在就 `SIGNAL` 中止，
提示改用 `db/migrations` 逐版本升级。`schema.sql` 从此只用于空库。

| 场景 | 结果 |
|---|---|
| 空库执行 schema.sql | 成功，版本 V1–V4，两个图标字段 `varchar(255)`，seed 正常 |
| V2 旧库执行 schema.sql | `ERROR 1644 检测到已有结构：请用 db/migrations 逐版本升级` |
| 拦截后检查 | 版本仍 V1,V2；icon 仍 64；数据 3/3/42 未变 |
| V2 旧库执行 V3 → V4 | 成功，版本 V1–V4，两个图标字段 255，数据 3/3/42 保留 |
| 重复执行 V4 | 被拒（"请勿重复执行"） |
