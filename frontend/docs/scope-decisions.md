# 前端范围与 P0 口径（2026-11-15 决策记录）

> 背景：小组评审提出「商品维护、规则编辑、订单履约在完成标准里是 P0，但前端只有列表页、没有写接口」。
> 本文记录本轮对这三项的处置，供组会确认与验收对照。

## 一、结论速览

| 功能 | 原状态 | 本轮处置 | 对外说法 |
| --- | --- | --- | --- |
| 订单履约 | 前端只能看列表 | **已补齐**：管理端订单抽屉「确认发放」+ 二次确认 | P0，已完成（v1） |
| 商品维护 | 前端只能看列表 | **已补齐最小版**：改积分单价、改库存、上架/下架 | P0（最小版），已完成（v1） |
| 规则编辑 | 前端只读 | **明确后置到 v1.1**：页面标注「只读 · 规则维护排期 v1.1」 | P1，后置（有理由，见第三节） |
| 商品新增/删除、图文维护 | 无 | 仍后置 P1 | P1，后置 |

## 二、已实现的部分（可直接演示）

1. 管理端 → 订单管理 → 点一行订单 → 抽屉底部「确认发放」→ 二次确认 → 状态变「已完成」。
   - 口径：**发放只改状态**，积分与库存在兑换时已扣减，发放不会二次扣减。
   - 后端契约：`POST /admin/orders/{orderId}/fulfill`，非「待发放」状态返回 409（`40903`）。
2. 管理端 → 商品管理 → 行内「编辑」改积分单价/库存，「下架」立即对用户端不可见。
   - 口径：**改价不追溯**，订单里存的是下单那一刻的单价快照。
   - 后端契约：`PATCH /admin/products/{productId}`，非法值返回 400（`40041`/`40042`）。
3. 越权保护：三个写接口都要求管理员身份，非管理员返回 403（`40301`）。

## 三、规则编辑为什么后置（组会可直接用）

修改排放因子会**改变同一段行程的核算结果**。要做对，至少需要四件事同时成立：

1. 规则版本化（新增版本而不是原地改）；
2. `effectiveFrom` 生效时间，历史行程按当时的规则口径核算；
3. 行程记录里保存 `ruleVersion` 快照（本项目已有此字段，但规则编辑功能未接）；
4. 变更留痕（谁、何时、为什么改）。

只做「能改数字」的半成品，风险比不做更大：历史积分会对不上账，而"积分对账"页正是本项目 P0 之一。
因此本轮把规则编辑定为 v1.1，页面上明确标注只读与排期，避免验收时被误读成"缺功能"。

## 六、2026-11-15 组长确认的三条口径

| 事项 | 结论 | 影响 |
| --- | --- | --- |
| 商品写接口形状 | **采用单个 `PATCH /admin/products/{productId}`**，不拆 `/status`、`/stock` 两个动作接口 | 前端无需改动；新增商品等 v1.1 再加 `POST /admin/products` |
| `TripStatus` 取值 | **保留 `PENDING` / `POINTED` / `FAILED` 三态** | 前端已有三态渲染；`FAILED` 是"为什么没加分"的唯一解释位 |
| 商品 `icon` 字段 | 类型定为 `varchar(255)` 字符串，**值先用 emoji** | 将来换 CDN 图片 URL 不用改表、不用改前端；禁止用 enum 或 `char(2)` |

补充说明：

- `PENDING` 若后端为同步核算，接口可以不返回该状态，但枚举保留，避免以后改异步时动契约。
- `POST /trips` 的 `tripId` 由服务端生成，`clientTripId` 只作幂等键；列表接口每条必须带 `tripId`（列表跳详情的唯一依赖）。
